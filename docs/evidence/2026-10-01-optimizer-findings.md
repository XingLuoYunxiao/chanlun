## F1 陈旧进程：网页显示 0 个买卖点（已修）

**现象**：重启前，`/api/structure?code=600030&limit=2000&adjust=qfq` 回 `signals: []`，
而同一个窗口在进程内直算（`ChanEngine(...).full(bars)`）回 **2 个**信号。
线段 16、中枢 3 两边完全一致 —— 只有信号不一样。

**根因**：`python -m chanlun serve` 的进程启动于 **11:58:41**，而口径修正
（`271ff95`，第三类买卖点按「位置」判定）提交于 **13:35:49**。
进程内是旧模块，`signal.py` 的修正没生效。

```
$ ps -o pid,lstart,command -p 1389
1389  四 10月/ 1 11:58:41 2026   ... -m chanlun serve
$ git log -1 --format='%h %ci' 271ff95
271ff95 2026-10-01 13:35:49 +0800
```

**为什么危险**：这是**假绿**的另一种形态 —— 代码、测试、审计全绿，
使用者看到的却是旧行为。凡是「改主干 → 看网页」的验收，必须确认
服务进程的启动时间晚于最后一次提交，否则截图证明的是旧代码。

**修复与复验**：重启进程（新 job）。重启后同一请求：

| 请求 | 重启前 | 重启后 |
| --- | --- | --- |
| `600030 limit=1200` | 买卖点 0 | 买卖点 **1** |
| `600030 limit=2000` | 买卖点 0 | 买卖点 **2** |
| `000002 limit=1200` | 买卖点 0 | 买卖点 **1** |
| `601398 limit=1200` | 买卖点 0 | 买卖点 **1** |

界面证据：`docs/evidence/2026-10-01-watchlist-ma-hfq.png`（已换成重启后的截图）。
自选栏出现 `三买 2025-04-07`（600030）、`三卖 2026-09-23`（000002）、
`三买 2025-01-22`（601398）三个标记；重启前那张同样的截图是「买卖点 0」。

**复现命令**：

```bash
curl -s 'http://127.0.0.1:8888/api/structure?code=600030&period=day&limit=2000&adjust=qfq' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["counts"])'
```

## F2 结构随可见窗口变（待定）

**现象**：同一个交易日、同一只票，只改「根数」，线段数、中枢数、买卖点数都会变。


**24/24 只票的线段数不同**，16/24 中枢数不同，17/24 买卖点数不同。
合计买卖点：1200 根窗口 **17** 个 → 全量 **45** 个 —— 默认视图只显示 38%。

**根因**：`web/api.py:snapshot_of()` 先按 `limit` 截断行情，再喂给引擎：

```python
df = _read_bars(code, period, limit)          # ← 先砍到可见窗口
...
snap = ChanEngine(code, period, signal_fn=find_signals, level=period).full(df)
```

笔、线段、中枢都是从**截断后**的第一根开始递归划分的，起点一变，划分就变。
而 `optimizer` 的审计脚本（`AUDIT_START = "2020-01-01"`，全量）算的是 43 个信号 ——
**仪表和产品量的不是同一个东西**。

**为什么算缺陷（而不是「设计如此」）**：spec 自己已经为价格定过同一条原则 ——

> 与当前可见窗口无关：某一天的后复权价是该日期的属性。
> 实现里一度取成「窗口首根所在的因子段」，于是同一交易日在 800 根窗口显示 28.9695、
> 在 1200 根窗口显示 31.5744……用户滚动窗口时整张图会平移。

（`docs/superpowers/specs/2026-10-01-tdx-data-watchlist-ma-design.md:123`）

线段/中枢/买卖点是**价格历史**的属性，同理不该是「可见窗口」的属性。
现在的实现等于把同一个 bug 留在了结构层。

**建议的修法**（改动集中在一处）：结构一律在**全量历史**上算，
只在**出图**时按 `limit` 裁剪标记与 K 线。

- `snapshot_of()`：取数不再带 `limit`（或带一个足够大的固定窗口），
  `limit` 只用于 `structure_payload()` 的显示裁剪；
- 缓存键里的 `limit` 可以去掉 —— 同一只票换根数不再重算（顺带变快）；
- `counts`（线段/中枢/买卖点）与图上标记一样，按可见区间过滤，
  保持「数字 = 图上画出来的东西」；
- 自选栏那个「中枢 未确认 ZG–ZD」的悬浮说明也会跟着变成窗口无关；
- 加两条测试：同一只票 `limit=300` 与 `limit=1200` 的**全量结构**必须逐字相同；
  可见区间外的标记不许出现在 payload 里。

**代价**：每请求多读几百到几千根 K 线（当前全量 1636 根，换 tdx 源后老票会到几千根）。
引擎算 38754 根（24 只票）在审计里是秒级，单只票的全量远小于此。

**不做的风险**：使用者把根数从 1200 调到 2000，会看到多出一整段线段、多出一个中枢、
多出几个买卖点 —— 他会认为这套东西在编结构。

## F3 除权因子覆盖率 0.1% → 85%（已修）

`adjust_factor` 表原来只有 4 只票（自选池那 4 只）有因子，全市场 5434 只有日线数据的票里
**99.9% 无法做后复权**（请求 hfq 会退化成 qfq，并给出「无除权因子，无法还原后复权」的说明）。

```bash
PYTHONPATH=src ../.venv-chanlun/bin/python -m chanlun factors --all   # 全市场反推
```

结果（`logs/factors_all.log`）：

```
written: 4653
no_change: 769
no_qfq: 36
thin_overlap: 11
no_raw: 2
因子反推(day): 4653/5471 只有因子，共 31160 段
```

- `written 4653` → `adjust_factor` 覆盖 **4653 只**、31161 段，`source` 全为 `inferred`；
- `no_change 769`：原始价与库内前复权价在重叠区间逐笔同价 —— 这段没有除权，
  本来就没有因子可反推，hfq 退化成 qfq 是**正确**结果，界面上有说明文字；
- `no_qfq 36 / no_raw 2 / thin_overlap 11`：无日线数据 / 无通达信原始价 /
  重叠不足 20 根，逐个都在日志里有票号。

**复现命令**：

```bash
PYTHONPATH=src ../.venv-chanlun/bin/python -m chanlun factors --codes 600030 --dry-run
sqlite3 data/meta.db 'select count(distinct code) from adjust_factor'
```
