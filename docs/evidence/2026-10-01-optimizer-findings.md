## F1 陈旧进程：网页显示 0 个买卖点（已修）

**现象**：重启前，`/api/structure?code=600030&limit=2000&adjust=qfq` 回 `signals: []`，
而同一个窗口在进程内直算（`ChanEngine(...).full(bars)`）回 **2 个**信号。
线段 16、中枢 3 两边完全一致 —— 只有信号不一样。

**根因**：`python -m chanlun serve` 的进程启动于 **11:58:41**，而口径修正
（`271ff95`，第三类买卖点按「位置」判定）提交于 **13:35:49**。
进程内是旧模块，`signal.py` 的修正没生效。

```
$ ps -o pid,lstart,command -p 1389
1389  四 10月/ 1 11:58:41 2026   ... -m chanlun serve
$ git log -1 --format='%h %ci' 271ff95
271ff95 2026-10-01 13:35:49 +0800
```

**为什么危险**：这是**假绿**的另一种形态 —— 代码、测试、审计全绿，
使用者看到的却是旧行为。凡是「改主干 → 看网页」的验收，必须确认
服务进程的启动时间晚于最后一次提交，否则截图证明的是旧代码。

**修复与复验**：重启进程（新 job）。重启后同一请求：

| 请求 | 重启前 | 重启后 |
| --- | --- | --- |
| `600030 limit=1200` | 买卖点 0 | 买卖点 **1** |
| `600030 limit=2000` | 买卖点 0 | 买卖点 **2** |
| `000002 limit=1200` | 买卖点 0 | 买卖点 **1** |
| `601398 limit=1200` | 买卖点 0 | 买卖点 **1** |

界面证据：`docs/evidence/2026-10-01-watchlist-ma-hfq.png`（已换成重启后的截图）。
自选栏出现 `三买 2025-04-07`（600030）、`三卖 2026-09-23`（000002）、
`三买 2025-01-22`（601398）三个标记；重启前那张同样的截图是「买卖点 0」。

**复现命令**：

```bash
curl -s 'http://127.0.0.1:8888/api/structure?code=600030&period=day&limit=2000&adjust=qfq' \
  | python3 -c 'import json,sys; print(json.load(sys.stdin)["counts"])'
```

## F2 结构随可见窗口变（已修）

**现象**：同一个交易日、同一只票，只改「根数」，线段数、中枢数、买卖点数都会变。

**根因**：`web/api.py:snapshot_of()` 先按 `limit` 截断行情，再喂给引擎：

```python
df = _read_bars(code, period, limit)          # ← 先砍到可见窗口
...
snap = ChanEngine(code, period, signal_fn=find_signals, level=period).full(df)
```

笔、线段、中枢都是从**截断后**的第一根开始递归划分的，起点一变，划分就变。
而 `optimizer` 的审计脚本（`AUDIT_START = "2020-01-01"`）在**同一份全量**上算的是 43 个信号
—— 仪表算的是全量、产品画的是窗口，**两边量的不是同一个东西**。
（43 与全史 45 的差是审计口径从 2020-01-01 起算带来的：只有 `300750` 有 2018–2019 的段，
它的 2 个信号因此不在审计里；其余 23 只票起点本来就在 2020 年，两种口径一致。）

**修复前的实测**（24 只票基准池，`limit=1200`；由 `optimizer/tools/measure_f2_window_scope.py` 生成）：

- **旧** = 先把行情砍到最近 1200 根再划分（缺陷口径）；
- **新** = 全量划分后裁到窗口（修复后）；
- **全** = 不设窗口的全史。

`601166`、`300760`）、**藏掉 21 个**（全史里落在窗口内、旧口径没画出来的）。
逐只不同：线段 **14/24**、中枢 **13/24**、买卖点集合 **18/24**。

**为什么算缺陷（而不是「设计如此」）**：spec 自己已经为价格定过同一条原则 ——

> 与当前可见窗口无关：某一天的后复权价是该日期的属性。
> 实现里一度取成「窗口首根所在的因子段」，于是同一交易日在 800 根窗口显示 28.9695、
> 在 1200 根窗口显示 31.5744……用户滚动窗口时整张图会平移。

（`docs/superpowers/specs/2026-10-01-tdx-data-watchlist-ma-design.md:123`）

线段/中枢/买卖点是**价格历史**的属性，同理不该是「可见窗口」的属性。
原来的实现等于把同一个 bug 留在了结构层。

**修法**（用户 2026-10-01 决策：「全量算结构，只按根数裁剪显示」）：

- 引擎一律喂**全量**帧：`_read_bars(code, period, None)`，`limit` 只用于显示；
- 新增 `Snapshot.clipped_to(first_ts, last_ts)`，裁剪规则是**相交就留** ——
  笔与线段首尾相接铺满时间轴，从中间切一刀必然有一段横跨左边界；把它丢掉，
  图上就会凭空断一段，留下的那一段由前端 category 轴线性外推到画布外，
  由画布裁掉，画出来仍是那条直线。**分型与买卖点是「点」**，没有横跨一说，
  必须严格落在窗口内（坐标不在轴上会被 ECharts 静默丢掉，图上看不出错，只是少个点）；
- `snapshot_of()` 改返回 `StructureView`（全量快照 + 窗口帧 + 全量 MACD + `totals`/`bars_total`），
  缓存键去掉 `limit`：换根数不再重算，顺带变快；
- **MACD 也走全量**：EMA 是递推量，窗口里重算种子就变，实测 `limit=500` 的柱子
  与全量尾部最大差 **0.0958** —— 那是两条不同的 MACD，拿它解释背驰就是自欺；
- payload 增加 `counts_total` / `bars_total`：`counts` 数**窗口里看得见的**
  （对得上图上画出来的条数），`counts_total` 数**全史**（说清还有多少没画）。

**修复后的实测**（同一基准池，`limit=1200`）：

| 口径 | 买卖点 | 说明 |
| --- | --- | --- |
| 旧（窗口内划分） | 17 | 其中 **2 个在全量划分里根本不存在**（幻影：`601166`、`300760`） |
| 新（全量划分裁到窗口） | **36** | 全史 45 个里落在最近 1200 根的 36 个 |

旧口径**藏掉 21 个真实买卖点、凭空造出 2 个幻影点**；线段数 **14/24** 只票与旧口径不一致
（换成新口径后线段数才稳定）。

**回归**：`tests/web/test_structure_window.py`（4 条，先红后绿）—— 划分逐字不随窗口变、
可见结构 = 全量 ∩ 窗口、MACD 与全量尾部逐位相等、只送与窗口相交的对象。
变异验证：把裁剪规则改成「完全落在窗口内才留」→ 立刻 1 条测试变红。

**复现命令**：

**UI 落点**（2026-10-01 真机验收补）：`counts_total` 一开始只活在接口里，页面上看不见，
用户会把状态栏「线段 12」读成「这只票只有 12 段」（全史 16 段）。右上角补一行，
**只在两边不一致时**出现：「全史 16 段 / 3 中枢 / 2 买卖点（这里只画与窗口相交的部分）」。
接口给数、页面说清「还有多少没画」——两件事都做完，F2 才算真的修完。

```bash

../.venv-chanlun/bin/python optimizer/tools/measure_f2_window_scope.py

# 产品侧：counts 是窗口里看得见的，counts_total 是全史
```

**99.9% 无法做后复权**（请求 hfq 会退化成 qfq，并给出「无除权因子，无法还原后复权」的说明）。

## F5 分钟周期没有范围约束：一次 `daily` 是 292 小时的活（已修）

**现象**：`config.toml` 的 `[data] periods = ["day","30","5"]`，`daily` 缺省就按它跑。
只要不显式给 `--codes`，`_resolve_codes()` 返回品种表全市场（5471 只），
三个周期**共用同一份代码列表**。日线走通达信整包无所谓，30/5 分只能逐只走 baostock。

**实测单只成本**（`logs/sync_watchlist_minutes.log`，自选池 4 只票跑完）：

| 周期 | 4 只耗时 | 单只 | 外推 5471 只 |
| --- | --- | --- | --- |
| 30 分 | 2 分 01 秒 | ≈30.4 秒 | ≈46 小时 |
| 5 分 | 10 分 48 秒 | ≈162.1 秒 | ≈246 小时 |
| 合计 | 12 分 49 秒 | — | **≈292 小时（12 天）** |

`daily` 是 launchd 每天 17:30 触发的：第二天 09:30 开盘前回不来，
第二天 17:30 又起一个 —— 两个进程同时打 baostock，还会互相抢 `meta.db`。

**为什么是缺陷（而不是「用户自己没加 `--codes`」）**：契约里早就写了范围 ——

> `tdx` 时日线走整包、30/5 分仍走 baostock（**只对自选池**）。
> 17:30 定时任务在 `source=tdx` 下日线同步从约 2 小时降到约 1 分钟。

（`docs/superpowers/specs/2026-10-01-tdx-data-watchlist-ma-design.md:183`）

但代码里**没有任何一处读自选池来决定范围**：`_resolve_codes()` 只认 `--codes`，
缺省即全市场；`_snapshot_all()` 与 `scan_report()` 也共用同一份代码列表 ——
「分钟只跑自选池」这条契约当时只活在文档和 plist 里。

**当时的缓解（不可靠）**：launchd 的 plist 写的是 `daily --periods day`，
恰好绕开了这个坑。但那是**部署脚本替代码兜底**：手敲一次 `python -m chanlun daily`
（或者哪天有人把 `--periods` 补回 `day,30,5`）就会踩中，而且踩中时没有一行日志提醒。

**修法**（用户 2026-10-01 决策：「补齐：分钟周期只跑自选池」）：

- 新增 `_codes_for_period(conn, period, codes, *, explicit)`：日线=给定范围；分钟=自选池。
  **显式 `--codes` 仍然照办** —— 用户自己圈定的范围已经是有界的，
  把明确点名的票悄悄丢掉比多跑几只更糟；
- `_period_scope()` 一次算清 `{period: 代码}`，**同步 / 结构快照 / 扫描共用同一份**
  （三处各写一套，迟早走散）；
- `scan_report()` 与 `_snapshot_all()` 增 `codes_by_period`（缺省 `None` = 旧行为，
  库层面的「全市场扫描」不受影响）；
- 单周期命令 `sync --period 30` 走同一条规则，堵住同一个洞。

**回归**（先红后绿）：`tests/test_cli.py::test_minute_sync_without_codes_uses_watchlist`、
`tests/test_daily_pipeline.py::test_minute_periods_are_scoped_to_the_watchlist`。
范围用**落库结果**观察，而不是断言「某个函数被调用过」：给非自选票也造一份新鲜的
30 分数据，范围没收住它就会被同步、被算出结构快照（修复前正是如此）。

**代价**：自选池为空时分钟周期什么也不做，`_usable_periods` 报
「本地无该周期数据」并降级为仅日线。这是**正确**的：没有自选池就没有要看的分钟级别，
而「静默什么都不跑」和「静默跑 292 小时」的区别，正是这条修复要保证的。

**复现**：

```bash
# 修复前：这一条会对品种表 5471 只逐只打 baostock（≈292 小时）
python -m chanlun sync --period 30

# 修复后：只对自选池，且摘要里的「共 N 只」就是自选池大小
python -m chanlun sync --period 30
```

单只成本来自 `logs/sync_watchlist_minutes.log`（4 只票的真实同步日志），
外推是 5471 × 单只耗时，不是估算出来的感觉。
