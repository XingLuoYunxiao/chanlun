# 一级 / 二级行业板块日线全量同步（2026-10-06）

## 0. 一句话

用户要求「同步一下这个一级行业、二级行业所有的这个数据」；申万板块清单里的
**155 个板块（一级 31 + 二级 124）全部落库**，共 **896,440** 根日线，末根一律
`2026-09-30`，`sync_state` 里 0 条 `error`。`GET /api/industries` 的「本地有数据」
从 **1 / 155** 变成 **155 / 155**，行业弹窗里当前一级 31 张卡**全亮**。

## 1. 怎么跑（可复现）

| 项 | 值 |
|---|---|
| 工作目录 | 项目根目录（`chanlun/`） |
| 代码清单 | `PYTHONPATH=src ../.venv-chanlun/bin/python -m chanlun industry --json` 的 `items[].code` |
| 同步命令 | `PYTHONPATH=src ../.venv-chanlun/bin/python -m chanlun sync --period day --codes "$CODES"` |
| 联网 | 经 `ALL_PROXY=socks5://127.0.0.1:7897`（见 §7 的口径提醒） |
| 耗时 | **2 分 47 秒**（`155/155 [02:47, 1.08s/只]`，baostock 单会话串行） |
| 落库位置 | `data/day/sw/<6 位码>.parquet`（`data/` 被 `.gitignore` 忽略，**不入库**） |

```bash
CODES=$(PYTHONPATH=src ../.venv-chanlun/bin/python -m chanlun industry --json \
  | python3 -c "import json,sys; print(','.join(b['code'] for b in json.load(sys.stdin)['items']))")
echo "$CODES" | tr ',' '\n' | wc -l        # ⇒ 155
PYTHONPATH=src ../.venv-chanlun/bin/python -m chanlun sync --period day --codes "$CODES"
```

| `sw.801780` 银行 | 6483 | 2026-10-06 20:16:32 | 已到最新交易日 |

### ★ 增量同步**不回补历史** —— 这次真的踩到了

`sw.801120` 早先只按 `--since 2026-09-01` 同步过，库里只有 **21 根**；
增量逻辑看到「本地末根已经是 `2026-09-30`（最新交易日）」就**跳过**，
所以这 21 根**不会**被自动补成完整历史。要回补必须显式全量重拉：

```bash
PYTHONPATH=src ../.venv-chanlun/bin/python -m chanlun sync --period day --full --codes sw.801120
# ⇒ 同步完成: 成功 1 失败 0 跳过 0（共 1 只）
# ⇒ sw.801120 现在: 5492 行 2004-03-01 .. 2026-09-30
```

里**独立**测得的该板块下界（`pt01801120` 翻页到底 = 5492 根、最早 `2004-03-01`）

## 3. 下界是不是真的到底（能失败的核对）

翻页循环有可能提前停（那样就会「静悄悄地少一段历史」）。核对办法：
**直接问数据商「比本地下界再早 10 天，还有没有数据」** —— 若翻页到底了，应回 0 行。

```python
sym = industry.vendor_code(code)            # sw.801120 → pt01801120
earlier = sw_source._page(sym, <本地下界 - 10 天>)
```

| 板块 | 本地下界 | 问数据商的日期 | 数据商回 | 结论 |
|---|---|---|---|---|
| `sw.801120` | 2004-03-01 | 2004-02-20 | **0 行** | 确实到底 |
| `sw.801780` | 1999-12-30 | 1999-12-20 | **0 行** | 确实到底 |
| `sw.801785` | 2016-09-09 | 2016-08-30 | **0 行** | 确实到底 |

三个板块分属三个不同年代（1999 / 2004 / 2016），都回 0 行。

## 6. 顺带修掉的：探针把「数据状态」写死成了常量

`2026-10-06-行业弹窗-旧后端页脚-probe.mjs` 第一版把期望值钉成
「恰好 1 张亮卡 / 页脚 `本地已有 1 / 155`」。这次同步之后**这两条判据必然误报** ——
它们测的本来是「页脚报的是不是**接口说的真值**」，而真值随本机数据状态变。

改成：期望值从 `GET /api/industries` **现算**（`EXP`），不写死。

### ★ 但只改成「现算」会引入一个**恒真**判据

数据全部同步完之后，`have` 恰好等于 `total`（155 == 155），于是

> 把 `const have = industryRows.filter((r) => r.local).length` 改成
> `industryRows.length`（即页脚改报总数），印出来的还是同一句话
> 「本地已有 155 / 155」—— **场景 B 那条判据分辨不出来**。

原来 `1 / 155` 时它能分辨（这正是它当初能抓住 `have` 恒报总数这个变异的原因）。
所以补了**场景 C**：把**一个** `local: true` 的板块改成 `false`，
让页面自己算出 `have ≠ total`，判据就不再依赖数据状态。

**变异实测**（把 `have` 改成 `industryRows.length`）：

```
FAIL  C 页脚报真计数（比总数少 1）
PASS  B 页脚报真计数          ← 同一个变异，B 照样绿（上面那段说的退化，实测如此）
15 / 16 PASS      退出码 1
```

还原后 `16 / 16 PASS`，退出码 0；`git diff --stat` 为空（用 `cp` 备份还原，
**没有** `git checkout --`）。

### 探针判据：12 → 16

| 场景 | 补丁 | 判据数 | 期望 |
|---|---|---|---|
| A | 摘掉每个 item 的 `local`（模拟进程比页面旧） | 8 | 页脚改口「后端进程比页面旧…」，一级卡全暗 |
| B | 不打补丁 | 4 | 页脚报真计数，亮卡数 == 接口说 `local` 的一级只数 |
| C | 把**一个** `local: true` 改成 `false` | 3 | 页脚报真计数（比总数少 1），亮卡数少 1 |
| 前置 | — | 1 | 本机至少一个板块有日线（否则 C 退化成 B） |

场景 A 的 `lit === 0` 与数据状态无关，**未改**。
