# 零行同步抹掉水位：235 只票被误判成「尚未同步」（2026-10-09，D-48）

## 0. 一句话

> **编号说明**：这次的问题**不是**任何一份「审查建议书」里的条目 —— 它没有编号，
> 是 2026-10-09 00:05 那次补回填**跑完之后**从 `meta.db` 里查出来的
> （`end_ts IS NULL` 的票从 0 变成 235），所以只挂 `D-48` 一个号，**不挂 `F-x`**。
> 理由同 D-47：仓库里已经存在**多套互不相干**的 `F-3`（见
> `docs/evidence/2026-10-08-定时任务静默挂死.md` §0），再挂一个只会更难查。

`sync.py` 的零行分支把 `meta.sync_state` 写成 `start_ts=None, end_ts=None, rows=0`。
下游 `scanner.check_sufficiency()` 看到 `start_ts` 是空串，就返回
「数据不足：meta.sync_state 无该周期记录（尚未同步），已跳过」，
`__main__._snapshot_all()` 见到 `not suf.ok` 就 `continue` —— **这只票当天不进结构快照**。

触发条件不是异常，而是**日常**：只要同步的 `end` 覆盖到一个「是交易日、但 bar 还没
发布」的日期（开盘前补跑就是），`start_for()` 就会去请求那根不存在的 bar，
数据源照实返回零行。**任何一只已经同步到最新交易日的票都会被清零。**

## 2. 现场：水位被清零，票被打成「尚未同步」

2026-10-09 00:05 的补回填跑在**交易日开盘前**。`start_for()`
（`src/chanlun/data/sync.py:37-53`）的逻辑是：

```python
last = store.last_ts(code, period)          # 本地最后一根 = 2026-10-08
nxt = cal.next_trading_day(str(last)[:10])  # 下一个交易日  = 2026-10-09
return None if nxt > end else nxt.isoformat()   # 10-09 <= 10-09 ⇒ 请求 10-09
```

`10-09` 是交易日，但当天 bar 要到收盘后才有 ⇒ **数据源返回零行**。
旧代码在零行分支写：

```python
meta.set_sync(conn, key, period, None, None, 0, adjust, error=None)
```

于是：

| 位置 | 值 |
|---|---|
| 本地 parquet 实际 | `rows=1394`，最后一根 `2026-10-08` |
| `sync_state` 被写成 | `start_ts=NULL`，`end_ts=NULL`，`rows=0` |
| `check_sufficiency()` 的理由 | 「数据不足：meta.sync_state 无该周期记录（尚未同步），已跳过」 |
| `_snapshot_all()` | `if not suf.ok: continue` ⇒ 当天不进结构快照 |

**这就是「不知道」被写成了「没有」**：库里明明有 1394 根，票却因为一次空手而归的
请求而自称从未同步。

## 4. 为什么这不是偶发

零行**不是**「数据源出问题了」的信号，而是「请求了一个还不存在的日期」的必然结果。
于是：

- **开盘前跑全市场** ⇒ 全市场 5471 只的水位一起归零。
- 这次只坏了 235 只，只是因为那次补回填**只覆盖了 235 只**（其余票的
  `start_for()` 恰好返回了别的值）。**范围是被输入限制的，不是被逻辑限制的。**
- 下一次同样的输入会得到同样的结果 —— 它是**确定性**的，不是竞态。

**D-47 的停批也看不见它**：`_sync_period` 在零行分支走 `skipped += 1` 并把
`consecutive` 归零（`src/chanlun/__main__.py:626-629`），所以「数据源整体返回空」
在停批统计里和「这些票本来就没事」长得一模一样。D-47 据此写下的
「零行 ⇒ 会话是活的」推断**是错的**（见 §6.1）。

## 5. 修复前后的行为差异

**改法**：新增 `_keep_watermark()`（`src/chanlun/data/sync.py:73-117`），
零行与异常两条路径统一走它：

```python
def _keep_watermark(conn, key, period, adjust, *, error):
    stored = store.read(key, period)              # 本地 parquet 才是真相
    if stored is not None and len(stored):
        meta.set_sync(conn, key, period, str(stored["ts"].iloc[0]),
                      str(stored["ts"].iloc[-1]), len(stored), adjust, error=error)
        return
    prev = meta.get_sync(conn, key, period)       # 本地也没有 ⇒ 守住上一行
    meta.set_sync(conn, key, period,
                  prev["start_ts"] if prev else None,
                  prev["end_ts"] if prev else None,
                  int(prev["rows"]) if prev else 0, adjust, error=error)
```

| | 修复前 | 修复后 |
|---|---|---|
| 零行且本地有数据 | `start_ts=NULL, end_ts=NULL, rows=0` | `start_ts/end_ts/rows` = **本地 parquet 的首末与行数** |
| 零行且本地也没有 | 同上 | 保留**上一行** `sync_state`，绝不写 `None` |
| 异常（真失败） | 写空 + `error=str(exc)` | 同上两条，**但 `error` 仍写入** |
| 分类 | 零行 = `skipped` | **不变**，仍是 `skipped` |
| `check_sufficiency()` | 「尚未同步，已跳过」 | 正常判据 |

**实测（能失败的测量）**：

新增三条护栏，**修复前三条都红**：

## 6. 被否决的替代方案

### 6.1 「水位落后于最新交易日、却拿到零行」⇒ 记 `failed`

这是本次最初打算采用的口径（也是 D-47 那句「零行说明会话是活的」的自然反面），
**实测否决**：

1. **它会制造 212 条永久假警报。** 那 212 只退市 / 长期停牌票
   **每跑一次都是「水位旧 + 零行」这个形状**。记 `failed` 等于给它们写一条
   **永远不会消失**的 `sync_state.error`：页面每次打开都在报错，
   每次运行的摘要都固定出现「失败 212」。**一个永远不清除的假警报比没有警报更糟**
   —— 它训练运维忽略失败计数，而失败计数正是 D-47 刚立起来的护栏。
2. **它并不能多识别出「数据源整体静默」。** 对那 212 只而言「零行」本来就是事实，
   把它们记成失败并不会让「整体静默」这个形状变得可分辨。
3. **指望「至少停批能兜住」也不成立 —— 实测兜不住。** 235 只里最长的连续号段
   只有 **9 只**（`000004`…`000012`），远低于 `MAX_CONSECUTIVE_FAILURES = 20`：

   ```console
   $ PYTHONPATH=src ../.venv-chanlun/bin/python - <<'PY'
   codes = "<冻结清单>".split()
   best, cur = [], []
   for c in sorted(codes):
       cur = cur + [c] if cur and c[:3] == cur[-1][:3] and int(c[3:]) == int(cur[-1][3:]) + 1 else [c]
       best = list(cur) if len(cur) > len(best) else best
   print(len(best), best[0], best[-1])
   PY
   9 000004 000012
   ```

   也就是说这条口径**买不到任何保护**，却要付 212 条永久假警报的代价。
   > **更正**：定这条口径时曾以为「235 只里有 72 只连续的 `600xxx`」。
   > 那是把**前缀分组计数**（`600 → 72`）误当成了**连续号段** ——
   > 那 72 只的号码是 `600068 600070 600077 600083 …`，间隔 2/7/6/3…，
   > **根本不连续**。实测最长连续段是 9 只，结论随之反转。

### 6.2 把 `end` 夹到「最后一个已发布的交易日」

需要一个「今天到底发布没有」的权威来源。baostock **没有**这种查询 ——
`query_trade_dates` 给的是**日历**，不是**可用性**。自己按时钟猜「17:30 之后
就算发布」是把交易日历换成猜谜，而且会误伤**开盘前手动补跑**这条合法路径
（本次补回填就是这种）。

### 6.3 让 `start_for()` 在「唯一候选日就是今天」时返回 `None`

这会把**当天 17:30 那次增量同步**一起砍掉 —— 而拉当天收盘那根**正是定时任务
存在的理由**。修 A 坏 B。

### 6.4 用 `universe.delisted` 当闸门

实测该列**没有在维护**：`000004`（国华退）等已退市票的 `delisted` 仍是 `0`。
它区分不出 212 与 23。

### 6.5 只修下游：让 `check_sufficiency()` 认为「`rows=0` 但本地有 parquet」也算够

这是把谎话留在 `sync_state` 里，只让**一个**读的人不信它。页面上的「本地 0 根」
与库里的 1394 根仍然自相矛盾，下一个读 `sync_state` 的地方会再踩一次。
**修数据，不修读数据的人。**

### 6.6 零行时干脆什么都不写（保留上一行原样）

比旧代码好，但仍不够：真·新股第一次同步拿零行时 `sync_state` 会**没有这一行**，
`check_sufficiency()` 照样报「尚未同步」；而且「水位落后」这个状态**永远不会自愈**
—— 它只在**下一次成功的同步**时才更新，而下一次可能同样是零行。
从本地 parquet 回填是唯一能让水位**当次就正确**的做法。
