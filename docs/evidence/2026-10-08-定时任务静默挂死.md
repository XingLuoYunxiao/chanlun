1. **给那个常驻 socket 装上超时**：`SOCKET_TIMEOUT = 30.0`，

## 3. 修复前后的行为差异（原样粘贴）

```console
$ cd /Users/zzz/workspace/chanlun
$ ../.venv-chanlun/bin/python optimizer/tools/measure_baostock_socket_hang.py
=== 黑洞服务端下的 fetch_bars 行为 ===
  修复后 SOCKET_TIMEOUT=0.3s：DataSourceError: baostock 登录失败: 10002007 网络接收错误。（0.3s）
  修复前 SOCKET_TIMEOUT=None：永不返回（20s 后由父进程杀掉）（20.01s）

  修复后必须秒级报错：通过
  修复前必须永不返回：通过
  结论：两路行为确实不同 —— 这次测量在测量东西
```

这就是**能失败的测量**：把 `SOCKET_TIMEOUT` 设回 `None`
（`socket.setdefaulttimeout(None)` = 阻塞，即修复前的行为），
这一路就永不返回。如果哪一天有人把 `bounded_login()` 删掉、
改回直接调 `bs.login()`，这个探针会立刻退回「永不返回」，
退出码从 0 变 1。

### 3.1 超时是怎么变成「正常错误」的

超时抛出后**不需要任何额外判据**，baostock 自己会把它翻成普通错误：

- `.venv-chanlun/.../baostock/util/socketutil.py` 的 `send_msg()` 的
  `except Exception` 吞掉 `TimeoutError`，返回 `None`；
- `.venv-chanlun/.../baostock/security/history.py` 第 106 行 把 `None` 翻成
  `data.error_code = cons.BSERR_RECVSOCK_FAIL`（`10002007`）、
  `data.error_msg = "网络接收错误。"`；
- `fetch_bars` 的既有重试分支（`error_code != "0"`）照原样接手：
  重登 → 再试 → 三次之后抛 `DataSourceError`。

所以上面那行 `10002007 网络接收错误。` 就是**超时**，不是别的毛病。
`bs.login()` 每次都新建 socket（`.venv-chanlun/.../baostock/login/loginout.py` 第 70-72 行 无条件
`SocketUtil().connect(...)`），所以「重登」这一步天然把那个坏掉的 socket 丢掉了。

### 3.2 为什么不是 `socket.setdefaulttimeout(30)` 就完事

那样会**改掉整个进程**的默认超时 —— 看盘页的 uvicorn 跟定时任务同源同进程时
会被一起改掉。`bounded_login()` 的做法是「只在登录那一小段里改，登录完恢复」：
socket 把创建时的默认值记在**自己身上**，所以常驻 socket 仍是带超时的，
而进程默认值原样还回去。

护栏测试 `tests/data/test_baostock_source.py::test_login_socket_carries_timeout_and_does_not_leak_process_default`
就是钉这一条的：它用一个假 `bs.login()` 在内部真建一个 `socket.socket()`，
断言（a）登录那一刻进程默认值 == `SOCKET_TIMEOUT`，
（b）那个 socket 自己的 `gettimeout() == SOCKET_TIMEOUT`，
（c）登录返回后进程默认值**恢复原状**。

另一条 `test_socket_timeout_is_a_finite_budget_not_a_hang` 断言
`0 < SOCKET_TIMEOUT <= 120` —— 防止有人把它设成 `None` 或一个大得离谱的值。

### 3.3 被否决的替代方案

| 方案 | 为什么不选 |
|---|---|
| 进程级 `socket.setdefaulttimeout(N)` | 泄漏进同进程的看盘页 |
| 工作线程 + `join(timeout)` | 阻塞的线程收不回来（会一直攒着），而且 baostock 是**单会话 socket**，多线程共用会串包 |
| 只在 `bs.login()` **之后**设超时 | 登录自己的 `connect()` / `recv` 仍然无界 |
| 猴子补丁 `SocketUtil.connect` | 改第三方库的代码，升级即失效；而且没必要 —— `setdefaulttimeout` 的作用域已经够用 |
| 加一个**永久**的黑洞端到端测试 | 它在修复前（红）状态下会**永远挂住**，把整个测试套件拖死。所以黑洞复现放在这份证据文档里（带 20 秒杀进程），套件里只放快的 `_SocketSpyBS` 护栏 |

## 4. 第二道防线：连续失败停批

超时把**单只**的最坏代价钉在 `3 × 30s + 2 × 1.5s ≈ 93s`，但 5471 只全这样
就是 **141 小时** —— 还是远超「下一个交易日开盘」这个硬期限。
所以 `_sync_period` 追加了计数器（`src/chanlun/__main__.py:607-631`）：

- `ok` ⇒ 清零；
- `skipped`（零行）⇒ **也清零**：零行意味着数据源**正常应答**了，会话是活的，
  它跟「失败」不是一回事；
- `failed` ⇒ +1，达到 `MAX_CONSECUTIVE_FAILURES = 20` 就 `break`，
  并把原因写进 `SyncOutcome.aborted`。

20 这个数是按**时间**选的，不是拍的：`20 × 93s ≈ 31 分钟`，
足够判断「今天这条链路是坏的」，也还留得住当天重跑的窗口。
停批后 `_daily_exit_code` 返回 1（`src/chanlun/__main__.py:903-918`）——
launchd 只记退出码，那是这条链路唯一能被外部看见的信号。
`SyncOutcome.summary()` 也会把停批原因印进每日摘要
（`src/chanlun/__main__.py:513-520`），免得「成功 20 失败 20」看起来像零星故障。

护栏测试 `tests/test_cli.py::test_sync_stops_batch_after_consecutive_failures`
（6 只票、阈值 3，断言只调用了 3 次且退出码非 0）与
`::test_sync_consecutive_counter_resets_on_success`
（`["ok","fail","fail","ok","fail","fail"]`，断言 6 只全跑完 ——
证明「清零」真的生效，否则第 5 只就会误触发停批）。

## 5. 顺带确认的两件事

### 5.1 定时任务**是存在的**，而且**确实触发过**


`-15` = 上一次退出是 SIGTERM（就是被手动 kill 的那次）。安装的 agent 在
`~/Library/LaunchAgents/com.chanlun.daily.plist`，模板在
`deploy/com.chanlun.daily.plist`，**工作日 17:30 Asia/Shanghai**，

### 5.2 用 17:30 而不是 17:00 是刻意的

baostock 的当日数据在收盘后要过一会儿才落定。`deploy/README.md` 记了这个理由。
另外**全市场 baostock 同步本身就是 2~6 小时**的量级（单会话串行 socket，
实测约 1.5~2 s/只 × 5471 只），这也是定时任务只跑 `--periods day` 的原因：
再叠 30/5 分钟周期必然撞上第二天开盘。
