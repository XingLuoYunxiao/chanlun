# 自选股读取失败的文案只能当**文本**渲染（2026-10-06，F-1 / D-45）

## 0. 一句话

`app.js` 里唯一一处把**变量**插进 `innerHTML` 的地方在自选股读取失败分支：
`box.innerHTML = \`<div class="watch-empty">自选股读取失败：${body.detail || "…"}</div>\``。
`body.detail` 来自 **HTTP 响应体**（跨进程边界），不是本文件的常量。修法是
`createElement` + `textContent` + `replaceChildren`。

真实浏览器 A/B（同一页面、同一份 payload，**只有那一处写法不同**）：

| 场景 | `#watch-rows` 里的失败文案（**含失败文案的那一张快照**） | `<img>` 元素 | `onerror` |
| --- | --- | --- | --- |
| A 磁盘上的 `app.js`（修复后） | `…失败：&lt;img src=x onerror="…"&gt;已损坏的响应` | **0 个** | **没触发** |
| B 拦截 `/static/app.js` 喂回旧写法 | `…失败：<img src="x" onerror="…">已损坏的响应` | **1 个** | **触发了** |

## 2. 改了什么

修复前（`app.js:1122`，全文件 6 处 `innerHTML` 中**唯一**带 `${` 的一处）：

```js
box.innerHTML = `<div class="watch-empty">自选股读取失败：${body.detail || "接口返回了无法解析的内容。"}</div>`;
```

修复后（`src/chanlun/web/static/app.js:1121-1129`）：

```js
    if (!body.items) {
      // `body.detail` 是响应体里的文本，不是本文件的常量 —— 只能走 textContent。
      // 交给 `innerHTML` 就等于让后端决定页面解析并执行什么标记（`tests/web/test_frontend_xss.py`）。
      const fail = document.createElement("div");
      fail.className = "watch-empty";
      fail.textContent = `自选股读取失败：${body.detail || "接口返回了无法解析的内容。"}`;
      box.replaceChildren(fail);
      return;
    }
```

修复后全文件的 `innerHTML` 站点（`grep -n 'innerHTML' src/chanlun/web/static/app.js`）：

## 3. 静态护栏：修复前必须变红

护栏文件：`tests/web/test_frontend_xss.py`（sha256 `af324d73978516b29842454f6f6b3edf0f4f5e543772b20ce2abe65bda2d0059`）。
三条断言：① 全文没有一行代码同时出现 `innerHTML` 与 `${`；② 那条失败分支里
没有 `.innerHTML =` 赋值，且有 `textContent` 与 `replaceChildren`；③ 用户看得见的
文案（`自选股读取失败：` / `接口返回了无法解析的内容。` / `body.detail`）都还在。

**①/② 只扫代码行、不扫整行注释**（`_code_lines()` 只丢整行注释）。理由：
修复后那句注释里**必然**出现 `innerHTML` 这个词，钉裸词会逼着后来的人删掉
「为什么禁用」的解释；所以断言钉的是**赋值**（`re.search(r"\.innerHTML\s*=", branch)`）
与「同一行同时有 `innerHTML` 和 `${`」这个机制，不是钉关键词。

```
终态快照：<div class="watch-empty">自选股是空的。把常看的票加进来，点一下就能看它的笔、线段、中枢和买卖点。</div>
4 / 4 通过
```

**注意 B 的 `real.imgCount` 也是 `0`** —— 因为失败文案已经被后到的
`renderWatch()` 盖掉了（见 §5）。也就是说：**只盯终态的话，这个漏洞是看不见的**
（终态里没有 `<img>`），而 `xssFired` 已经变成 `true` 了 —— 脚本在文案被替换之前
就执行了。这正是判据必须钉「含失败文案的那一张快照」+「`onerror` 有没有触发」
而不是钉终态 `imgCount` 的原因。

判据（A 侧 8 条、B 侧 4 条）全部通过。B 侧那 4 条正是 A 侧的**可失败性证明**：
同一条 payload 走旧写法会长出真正的 `<img>` 且 `onerror` 真的执行
（`window.__xss_real === 1`）—— 所以「A 里没有 `<img>`」不是因为 payload
不是标记，而是因为它被当文本写了进去。

**为什么不钉终态**：`setCode()` 会调 `renderWatch()`（`app.js:223`、`app.js:233`），
它无条件 `box.innerHTML = ""` 再从 `state.watch` 重画。启动时 `load()` 先于
`loadWatch()` 发出，后到的 `renderWatch()` 会把失败文案盖掉，所以终态是
「自选股是空的」。探针用 `MutationObserver` 记下 `#watch-rows` 的**每一次**状态，
判据钉在「含失败文案的那一张快照」上。

## 5. 顺带量到的一件事：**失败文案会被后到的 `renderWatch()` 盖掉**

`hist` 显示的顺序在两个场景里**一模一样**：先写失败文案，再被
「自选股是空的」替换掉。这不是本次改动引入的（场景 B 用旧写法也是同一顺序），
而是既有的**排序**问题：

- `loadWatch()` 的响应先到（探针里是立即 resolve）⇒ 写入失败文案；
- `load()` 的续段随后调 `setCode()` ⇒ `renderWatch()` 拿 `state.watch`（仍是 `[]`）
  重画 ⇒ **把「读取失败」说成「自选股是空的」**。那又是一句错话，
  和 D-44 页脚那次同属一类（「不知道」与「没有」长得一样）。

**本轮不修**：修它要动 `renderWatch()` / `setCode()` 的调用时序，
超出 F-1 的范围（用户本轮只授权 F-1 + F-2 + F-3）。已按 `AGENTS.md` §1
登记为已知空白（`ARCHITECTURE.md` §5、`CHANGELOG.md` 的
`### 已知空白与未实现项`）。
