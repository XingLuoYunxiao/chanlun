# 打开某只票就自动把它补到最新：按需拉取验收（2026-10-10，D-49）

## 0. 一句话

> **编号说明**：这次不是任何一份「审查建议书」里的条目，是用户 2026-10-10 直接提的
> 需求 —— 原文见 §2.0。所以只挂 `D-49` 一个号，**不挂 `F-x`**（仓库里已经有多套互不
> 相干的 `F-3`，再挂一个只会更难查；理由同 D-47 / D-48）。

定时任务交付不了的「最新」，改成「**你打开哪一只，就补哪一只**」：
判据全在后端（`/api/structure` 的 `stale` / `syncable` / `expected_as_of`），
前端只做后端做不了的两件事 —— **什么时候去问**、**问过几次**。

整场验收里浏览器一共开了 **8 次页面**（含 4 次页面内换票），服务端只收到
**3 次 `POST /api/sync`**，对应的正是那 3 只**真的落后**的票；
其余 5 次（含 2 次"换回同一只"）**一个同步请求都没发**。

## 3. 验收（可失败的测量）

### 3.1 布局零位移：真浏览器三态 rect 逐字节相同

浮标是一个**绝对定位**的小条，插在 `.stage` 里、`#notice` 之外。
下面是同一个页面（`?code=sh.000001&period=day`，1600×1000）在三种状态下的
`getBoundingClientRect()` 与文档尺寸：

| 量 | ① 自然（隐藏） | ② 强制显示（最长文案 + 可点样式） | ③ 把浮标整个 `remove()` |
|---|---|---|---|
| `#chart` | h684 w954 top228 left310 | **同左** | **同左** |
| `.stage` | h759 w954 top153 left310 | **同左** | **同左** |
| `#stamp` | h34 w541.9 top21 left1038.1 | **同左** | **同左** |
| `#stamp-detail` | h42 w1600 top77 left0 | **同左** | **同左** |
| `body` 的 `grid-template-rows` | `77px 42px 34px 760px` | **同左** | **同左** |
| `body` 直接子元素个数 | 7 | **同左** | **同左** |
| `#notice` 的 `display` | `none` | **同左** | **同左** |
| 浮标是不是 `#notice` 的孩子 | `false` | **同左** | **同左** |
| 文档 `scrollHeight` / `scrollWidth` | 913 / 1600 | **同左** | **同左** |
| 浮标自身 rect | h0 w0 top0 left0 | h50 w420 top850 left826 | 不存在 |
| 浮标父节点 | `stage` | `stage` | `null` |

**只有浮标自己那一行在变，其余九行三态完全相同。** 这就是「不许动现有布局」
（设计文档 §4.6）的可失败测量：一旦有人把浮标写成文档流里的元素（或塞进 `#notice`），
`#chart` 的 h/top 立刻会变，这张表就会对不上。

浮标自己的几何也对着设计文档：

- 右：`826 + 420 = 1246`，`.stage` 右边界 `310 + 954 = 1264` ⇒ 距右 **18px** ✓
- 下：`850 + 50 = 900`，`.stage` 下边界 `153 + 759 = 912` ⇒ 距下 **12px** ✓
- 宽：`min(420px, 60%)`，`60% × 954 = 572.4` ⇒ 取 **420px** ✓

### 3.2 已知最新 ⇒ **一个请求都不发**

`?code=sh.000001&period=day`（末根已是 2026-10-09）：

```bash
echo "before=$(grep -c 'POST /api/sync' /tmp/serve.log)"
node /tmp/dsh_cdp_eval.mjs "http://127.0.0.1:8888/?code=sh.000001&period=day&cb=$RANDOM$RANDOM" 6000 \
  '({顶栏:$("#stamp").textContent, chip可见:!$("#sync-chip").hidden, chip文案:$("#sync-chip").textContent})'
echo "after=$(grep -c 'POST /api/sync' /tmp/serve.log)"
```

实测：

| 量 | 值 |
|---|---|
| `POST /api/sync` 增量 | **+0**（`before = after`） |
| `/api/structure` | `status 200, code "sh.000001", as_of "2026-10-09", stale false, syncable true, expected_as_of "2026-10-09"` |
| 顶栏 | `sh.000001 上证指数 · 日线 · 截至 2026-10-09` |
| 浮标 | 存在，`hidden === true`，`textContent === ""`（再等 400ms 仍是空） |
| 浮标父节点 | `stage`（不是 `#notice`） |

**这就是"自动拉取"和"每次打开都拉一遍"的分界线**：判据来自后端，
`stale !== true` 就**一个请求都不发**（`app.js:614`）。

### 3.3 落后 ⇒ **恰好一次 POST**，补完就停

`?code=600519&period=day`（末根 2026-10-08，落后一根）。浮标文案的**时间序列**：

| 时刻 | 浮标 | 可见 |
|---|---|---|
| 0.0s | `正在补最新数据：本地截至 2026-10-08，最新交易日 2026-10-09…` | 是 |
| 1.8s | `已补到 2026-10-09` | 是 |
| 5.8s | `已补到 2026-10-09` | **否**（自己收起来） |

| 量 | 值 |
|---|---|
| `POST /api/sync` 增量 | **+1**，之后再等 6 秒**没有第二次** |
| 顶栏（补完自动重画） | `600519 贵州茅台 · 日线 · 截至 2026-10-09` |
| 复查 `/api/structure` | `as_of "2026-10-09", stale false` |
| 访问日志（`/tmp/serve.log`） | `L37 GET …code=600519… → L44 POST /api/sync → L54/L55 GET …code=600519…` |

同一个测试在**带前缀**的书签上也一样（`?code=sh.601288&period=day`，
末根 2026-10-08）：0.0s `正在补…` → 1.8s `已补到 2026-10-09`，
顶栏 `601288 农业银行 · 日线 · 截至 2026-10-09`，`POST` 增量 **+1**。

> **单只同步可能很慢，浮标必须如实说"正在补"。** 实测 `?code=sh.601398` 那一次
> 用了 **26.8 秒**：`/api/sync/status` 自报
> `{"state":"done","rows":4847,"start_ts":"2006-10-27","end_ts":"2026-10-09","elapsed":26.8}`，
> 日志里能看到 `[Errno 60] Operation timed out` + `10002007 网络接收错误` 后**重试成功**。
> 这正是"POST 只负责排队、前端轮询"（`app.js:491`/`537`）而不是同步等结果的原因。

### 3.4 换票 / 二次进入：一次会话里一只票只自动补一次

在**同一个页面**里走真实表单换票（`#code.value` + 在 `#query` 上派发 `submit`），
每一步等 9 秒再读数：

| 步 | 操作 | 顶栏 | 浮标 | `POST` 增量 |
|---|---|---|---|---|
| ① | 初始 `sh.000001`（最新） | 截至 2026-10-09 | 隐藏、空 | 0 |
| ② | 换到 `601088`（本地 10-08） | **截至 2026-10-09** | 隐藏（已自动消失），文案 `已补到 2026-10-09` | **+1** |
| ③ | 换回 `sh.000001` | 截至 2026-10-09 | **隐藏、文案清空** | 0 |
| ④ | 再换回 `601088`（本次会话第二次） | 截至 2026-10-09 | 隐藏、空 | **0** |

③ 咬的是**缺陷 A**（§4.1）：换票第一件事就是收浮标，不许把上一只的结论留在图上。
④ 咬的是**反循环**：`autoTried` 在飞之前就登记（`app.js:646`），
补完的 `load()` 不会再触发自己。

### 3.5 补了也没有新数据（停牌）⇒ 可点重试，但**不自动重试第二次**

`sz.002898`（赛隆退，末根 2026-07-16，长期停牌；后端 `sync_one` 零行 ⇒
`state: "skipped"`）：

| 步 | 浮标可见 | 浮标文案 | class | `pointer-events` | `POST` 增量 |
|---|---|---|---|---|---|
| ② 第一次进 | 是 | `没补到新数据：本地记录已是最新，文件里还没有新数据 · 点这里重试` | `sync-chip is-retry` | `auto` | **+1** |
| ③ 同一会话再进 | 是 | `没补到新数据：本次会话已经自动补过一次，没有再自动重试 · 点这里重试` | `sync-chip is-retry` | `auto` | **0** |

顶栏两次都是 `002898 赛隆退 · 日线 · 截至 2026-07-16`（数据确实没有变），
所以**必须**给一个看得见、点得动的重试 —— 静默 `return` 等于把失败一起藏了。

> `skipped` 的文案是**故意**和手动路径不一样的：这次行情源**根本没被问到**
> （`sync.py:190-191` 的 `start is None` 短路），所以不许写"行情源没有返回数据"。

### 3.6 拉不了的组合（指数分钟线）⇒ 不发 POST，404 里也带 `expected_as_of`

`?code=sh.000001&period=30`：

| 量 | 值 |
|---|---|
| `/api/structure` | `status 404` |
| `syncable` | **`false`** |
| `sync_hint` | `sh.000001 是指数，baostock 不提供指数的分钟线，同步这个周期只会空跑。指数看日线/周线/月线即可（周月线由本地日线聚合）。` |
| `expected_as_of` | **`2026-10-09`**（404 也照报，前端才不用自己算日历） |
| `POST /api/sync` 增量 | **+0**（等了 2.5 秒，浮标始终隐藏） |
| `#notice` 文案 | `没有这只票的本地数据sh.000001 的 30 周期没有本地数据，而且补不了：…` |

**这里刻意不发请求**：给一个必然被拒的按钮，比不给更糟 —— 用户点了、等了、
被拒了，才知道这条路是死的（`app.js:222-230`）。

## 4. 实施中发现并修掉的缺陷（都是真浏览器测出来的）

设计文档 §4.5 记了这件事：**按需拉取写完之后，真浏览器一跑就露出三个同根因缺陷**，
它们**没有一个**能被静态断言拦住 —— 这正是 AGENTS.md §4「UI 相关改动必须用真实
浏览器核对」的实例。

### 4.1 缺陷 A：浮标没绑在「你正在看的这一只」上

**现象**（2026-10-10，修复前）：在退市股 `sz.002898` 上补不到，浮标变成可点的
「点这里重试」；随后换到已经最新的 `600000`，那行字**仍然挂在图上、仍然可点**，
点下去补的还是 `002898`。同一个窗口里「已补到」那条也会在自动消失的 4 秒里挂到别的票上。

**修法**：给浮标记归属（`chipJob`），三个地方都先问一句"你现在讲的是不是这一只"：

- `chipIsAbout(job)`（`app.js:598`）—— 归属判据
- `load()` 里 `if (!chipIsAbout(chipJob)) dropChip();`（`app.js:202`）—— 换票第一件事就收，
  **在 `await` 之前**，否则会留下几百毫秒的错位窗口
- `chipState()` 里 `if (!chipIsAbout(job)) return;`（`app.js:691`）—— 后台补完的别人，
  一个字都不许写到当前这张图上

**证据**：§4.3 第一张表（单元级变异）与第三张表（浏览器级变异）。

### 4.2 缺陷 B：**落库键** vs **用户输入原样**（同一个根因，三处）

`state.code` 是**用户输入的原样**（书签可以是 `?code=sz.002898`），
`state.key` 是服务端回的**落库键**（`002898`）。两者**不同形态**，而且方向还不一样：

| 请求 | 服务端回的落库键 | 为什么 |
|---|---|---|
| `?code=sz.002898` | `002898` | 股票前缀可以省 |
| `?code=600000` | `600000` | 同上 |
| `?code=sh.000001` | **`sh.000001`** | 指数**必须**留前缀，否则和 `sz.000001` 平安银行撞号 |

拿输入原样比身份，就出了三处缺陷：

| 编号 | 症状 | 现场 | 现在用 |
|---|---|---|---|
| B1 | 浮标**一个字都不显示** | `chipIsAbout` 拿落库键 `job.code` 比输入原样 `state.code` | `app.js:599` |

## 5. 顺带改正：一条在 HEAD 上就已经指错的老引用

改 `ARCHITECTURE.md` §5 那张表时发现，**HEAD 上就已经错**（不是这次改坏的）：

- 原句：`setCode()` 会调 `renderWatch()`，而它引的 `app.js:233`、`app.js:258`
  在 HEAD 上**两行都在 `load()` 里面**。
- 改成：`load()` 会调 `renderWatch()`（`app.js:247`、`app.js:258`）。

**行号引用指纹护栏的两个陷阱**（这次都踩到了，记下来给下次）：

1. 基线的 key 是 `文件名:范围文本#文档内出现序号`，**不含文档行号**。
   D-45 那行的 `app.js:233` 挪到 `app.js:258` 之后，新 §5 行里一个**合法**的
   `app.js:233` 变成了该 key 的 `#0` 出现，于是拿旧指纹一比就报"不符" ——
   这不是真漂移，`--update-baseline` 重记即可（**但要人确认意图**，
   因为 `--update-baseline` 会把任何现存内容"祝福"成基线）。
2. 同一个 key 碰撞还会**误改**别的引用：D-49 条目里的
   ``（`app.js:233`）`` 被自动重锚成了 `app.js:258`，**那是错的**，已改回。

**重锚纪律**：一律按**内容**找新行号（`git show HEAD:<file>` + 内容匹配），
**绝不用 `+N` 平移**；重锚完必须重新计算指纹**并且**读一遍被引的那一行。

## 6. 这次**没有**修的东西

1. **定时任务仍然没有覆盖率报告，也没有补跑。** D-49 只在"你打开它"时补。
   2026-10-09 那次的摘要只说了「成功 268 失败 22 跳过 35」，**没有一个字**提到
   "全市场还差 5203 只"——这是 §2.1 那张表存在的原因。
   缺口**会自愈**（`sync.py:37-53` 的 `start_for()` 从 `next_trading_day(末根)` 续拉），
   但"哪一天漏了"这件事本身仍然没人报。
2. **指数与港美自选仍在 `universe` 之外。** §2.2 里 8 只落后，D-49 只在你打开它们时补。
3. **本地一根都没有（404）时，自选按钮与高亮仍可能误报。**
   `app.js:233` 的 fallback 把 `state.key` 记成请求原样；此时 `?code=sh.600759`
   而本地无数据 ⇒ ★ 仍显示「加自选」。修法要后端在 404 body 里也回 `code`。
4. **"补一次"是会话级的**：刷新页面 = 新会话，会再补一次。
   这是**有意**的（刷新后前端确实不知道之前补过），但它意味着"反复刷新一只停牌股"
   会反复发请求 —— 每次都是 `skipped`，不联网，代价是一次本地查询。
5. **单只同步可能很慢**（§3.3 实测 26.8s）。浮标只能如实说"正在补…"，
   没有进度条，也不能取消。
6. **`chanlun sync` 仍可绕过交易日闸门** —— 本功能正是靠这一点，
   所以它是特性，不是缺陷；但它也意味着"用命令行补"和"页面自动补"走的是同一条路。
